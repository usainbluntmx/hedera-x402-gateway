The problem

Agents that pay for themselves need limits they can't talk their way around.

x402 lets software pay software with no human in the loop. That's the point — and the risk. A prompt injection, a bad loop, or a misconfigured budget shouldn't be able to drain a wallet one micropayment at a time.

Without a guardrail

The agent is the only limit

Every x402 client signs whatever it's told to sign. If the agent misbehaves, nothing between it and the blockchain says no.

With this gateway

The limit is checked before the signature

Per-transaction and daily caps — global or per agent — are evaluated the moment a payment is proposed, not after it's already settled.

How it works

Five pieces, one execution order.

Each step runs on real Hedera testnet rails — not a simulation layered on top.

01

Any route becomes pay-per-request

One middleware call turns an ordinary Express route into an x402 resource — settled in native HBAR or USDC, whichever fits how you price.

HBAR + USDC settlement
02

The guardrail checks before signing

The buyer's proposed payment is evaluated against its policy — a custom per-agent limit, or the global default — before any transaction is built.

03

The payment settles on-chain

x402's exact scheme constructs and settles a real Hedera transfer through the standard facilitator — verifiable independently on HashScan.

04

Every settlement is stamped to HCS

A message documenting the payment is submitted to a dedicated Consensus Service topic — an audit trail that survives even if this server disappears.

Consensus Service
05

Agents can pre-authorize the future

A single call schedules a payment days in advance. Hedera's network executes it autonomously — no signer needs to be online when it fires.
